# Sub2-Mac 后续改造优化方案

> **优先级已于 2026-09-08 按用户要求调整。** 当前以[前端执行计划](frontend/EXECUTION_PLAN.md)为准：前端质感与组件框架优先，直接对接原版后端；网关、支付、生产部署不作为本轮前置项。以下保留为全项目历史建议。

基线日期：2026-09-08。依据：[项目审阅报告](PROJECT_REVIEW_2026-09-08.md)。

## 目标与优先顺序

主定位为 **Sub2API 的桌面风格 Web 控制台**。优先使运营者和 API 使用者可靠完成业务任务；macOS 风格承担导航、视觉识别和多窗口协作价值。

保留 Vue 3、TypeScript、Pinia、现有 API 客户端、窗口组件和已经接入的业务页面。采用增量改造，不进行框架重写，也不按“每个上游接口都生成一个 App”的方式扩张。

成功标准：

1. 用户能登录、创建密钥、查看真实用量、完成订阅或充值，并在失败时恢复。
2. 管理员能配置账号与路由、定位异常、处理订单；危险操作针对明确对象，只执行一次。
3. 展示的金额、状态、能力和版本均可追溯；未知、失败、过期与真实零值分开表达。
4. 同一前端产物能在声明支持的后端版本上运行，新机器可复现部署、升级和回滚。
5. 多窗口提升跨对象操作效率；小屏至少完成用户端核心任务。

**工作假设**：近期服务一个 Sub2API 产品，而不是同时发展通用桌面框架。如果后续明确第二个业务系统，应以真实复用需求调整包边界。

## 阶段 A：先消除交付阻断

目标：开发和验收环境可以继续使用，公网与真实交易有明确安全边界。

| 编号 | 工作与最小改动点 | 完成标准 |
| --- | --- | --- |
| A1 | 修复 `server/gateway.js` 支付回调拦截。确认对应后端版本的回调入口，由可信后端完成验签、幂等和入账；网关不自行返回支付成功 | 沙箱回调携带原始字节、请求头到达后端；无效签名和未知订单不能成功入账；重复回调只入账一次；失败响应保留后端语义 |
| A2 | 静态服务仅允许独立发布目录。移除原型缺文件时回退项目根目录的逻辑；缺少构建时启动失败；若保留演示，以单独目录/进程提供 | 使用不含敏感信息的哨兵文件验证：源码、配置、日志、备份、可执行文件及目录外路径均不可下载；正确资源仍可读取 |
| A3 | 固定代理上游协议、主机和端口，只允许请求改变路径及查询；显式处理非法请求目标。按实际需要限制跨域与可信转发头 | 绝对 URL、双斜线目标、非法 Host 不得改变上游或导致进程异常；合法 HTTP/SSE 请求仍可用；需要 WebSocket 时另行验证升级转发 |
| A4 | 将配置改为模板，明确环境变量/私有配置注入方式。清除浏览器中的空密码默认值；建立二进制来源、格式、版本、哈希清单 | 不携带可直接使用的默认管理凭据；必需配置缺失时明确失败；修复 ZIP 被当作 EXE 启动；平台程序可核验 |
| A5 | 建立前端统一启动与会话服务。所有 Dock、菜单、Finder、Spotlight、URL 和恢复窗口入口调用同一启动策略；调试入口仅在开发环境启用 | 未登录不能挂载受保护业务视图；普通用户不能打开管理视图；退出、换号、权限收回后清理窗口与缓存、取消旧请求，并拒收旧会话响应。另用普通用户真实令牌验证管理接口拒绝访问 |
| A6 | 集中处理删除、禁用、余额调整、重启与回滚确认。先修直接删除和 `MacAlertSheet` 的全局 Enter 行为 | 确认显示对象与影响；仅最上层活动弹窗接收键盘事件；加载中不能再次确认；多窗口、最小化窗口和快速连按均只触发目标操作一次 |

配置凭据是否曾用于对外环境需要查验；确认暴露范围后再制定轮换及会话失效步骤。本阶段不通过修改前端角色判断来替代后端授权。

**阶段出口**：A1–A6 的关键用例通过，才进入真实商业链路验收。仅类型检查、构建成功或健康接口 200 不构成阶段出口。

## 阶段 B：让功能与业务状态可信

目标：交付一条完整用户路径和一条完整运营路径，同时清除“看起来成功”的状态。

| 编号 | 工作与最小改动点 | 完成标准 |
| --- | --- | --- |
| B1 | 在登录启动流程读取公共能力：注册、邮箱验证、验证码、邀请、推广归因、TOTP、OAuth、Passkey。按已验收能力显示入口 | 关闭注册、开启验证码、启用邮箱验证等组合不会把用户带入必然失败的流程；会话过期可重新认证并返回允许访问的任务；暂未支持的能力明确说明 |
| B2 | 以 `api/client.ts` 为统一错误出口，桌面服务订阅会话/能力变化；补齐合规确认和敏感操作二次验证；修正传统路由恢复逻辑 | 401、403、423、429、超时和能力关闭有可读提示、影响范围与恢复动作；请求失败不会显示“没有数据”；授权完成后明确确认是否继续原操作 |
| B3 | 建立设置表单与 `UpdateSettingsRequest` 的显式读写映射，移除整对象 `as any`；未加载成功前禁用保存；只提交当前模块改动 | API 端点、协议开关及条款使用真实字段；读取失败不会提交默认值；保存回读一致；并发编辑可检测冲突 |
| B4 | 修复设置子保存函数吞错。每项返回明确结果或继续抛错，由聚合层展示成功/失败明细 | 四项设置中一项失败时，不出现全量成功；保留未保存输入，只重试失败项；具体错误不丢失 |
| B5 | 补齐钱包订单状态机：支付方式、二维码/跳转、查单、订阅 `plan_id`、退款与恢复 | 下单后能到达订单终态并回读余额或权益；重复点击、刷新、中断、过期、取消、失败可恢复；按钮有真实动作 |
| B6 | 按供应商和认证类型建立账号录入表单与序列化，先修 `api_key` / `apikey` 枚举不一致 | 默认 API Key 录入可用；OAuth、Bedrock、Service Account 等组合使用相应契约；暂未接入的组合不可伪装为可用；编辑控件与提交字段一致 |
| B7 | 统一远程数据状态：`idle/loading/success/empty/error/stale`。移除假余额、固定指标、假更新检查与错误零值 | 断网、未登录、首次加载、后台关闭功能和过期缓存时不显示虚构正常状态；金额/用量单位跨页面一致 |
| B8 | 分离网关进程存活、后端就绪与业务可用状态。统一 `buildApiUrl` / `buildGatewayUrl`，修复终端等硬编码地址 | 外部域名、HTTPS 与自定义 API 基址下请求同一目标；后端不可达时不能报告上游健康；HTTP 成功不冒充模型可用 |
| B9 | 建立按业务场景组织的能力矩阵，给 23 个视图标注读、写、恢复路径与后端版本 | 每项核心能力有验收记录；API 文件存在但无界面/契约验收的功能不标记“完成”；处理列表截断、完整导出、用户公告等实际缺口 |

建议先完成的两个纵向场景：

**API 使用者**：登录 → 创建有权限的密钥 → 使用测试额度进行一次获准的模型请求 → 查看请求明细与费用 → 查看余额或订阅变化。

**运营者**：新增专用测试账号 → 绑定分组/渠道 → 执行探测 → 查看调度与错误证据 → 禁用或删除测试对象 → 确认影响及审计记录。

支付单独验收：创建订单 → 支付平台沙箱 → 回调验签与幂等 → 订单终态 → 余额/订阅入账 → 退款或取消。刷新、重复点击、超时和重复回调必须覆盖。

金额、时间窗口、倍率和订阅额度以固定后端契约为准，不在前端重新实现结算规则。

## 阶段 C：建立可复现交付

此阶段的基础工作可与 B 并行；生产验收依赖 A、B 的关键路径通过。

| 编号 | 工作与最小改动点 | 完成标准 |
| --- | --- | --- |
| C1 | 确认本目录对应的版本库，建立源码基线、忽略规则、工具版本声明和最小 CI | 干净检出使用锁文件安装，类型检查、构建及关键测试通过；运行数据、密钥、浏览器配置和备份不进入发布 |
| C2 | 建立上游来源与兼容清单：仓库、提交/版本、镜像 digest 或二进制 SHA-256、平台、配置模式、已测能力 | 可回答“这个前端配哪个后端”；不得仅以 `latest` 或文件名证明兼容 |
| C3 | 将 Compose 草案改为独立构建和部署配置；运行时只携带必需文件；按后端真实契约配置数据目录和依赖 | 新机器从声明的输入启动；资产无缺失；数据库和文件类数据持久化；不挂载整个工作目录作为服务根 |
| C4 | 开发启动器显式定位工作目录、检查依赖与进程身份、轮询就绪并在失败时退出 | 任意工作目录启动行为一致；端口被其他程序占用时不误判；依赖异常不会继续宣称全部服务启动 |
| C5 | 建立版本标识、健康/就绪、日志脱敏和回滚合同；核验后端维护按钮适用于二进制还是容器 | UI 明确当前部署模式；不支持的原地更新被禁用；回滚保留兼容数据且完成一次恢复演练 |
| C6 | 核对代码、图标、壁纸与二进制的来源和许可记录 | 发布清单有来源与使用依据；缺少依据的素材替换或从发布中移除 |

网关选择先按需求判断：若只需静态托管、HTTP/SSE/WebSocket 代理，优先评估已有反向代理能否满足。只有存在明确的产品适配职责时才保留 Node 层，避免再造支付或鉴权后端。

在建立版本基线后，将根目录与归档中的两份旧原型收敛为一个显式演示入口；不直接删除尚未登记的资产或备份。当前根目录资源与主线 `public/assets` 已有差异，应先建立清单再归并。

## 阶段 D：降低维护和操作成本

| 编号 | 工作与最小改动点 | 完成标准 |
| --- | --- | --- |
| D1 | 应用按需加载，保留统一注册表；按业务访问拆包，观察共享图表依赖 | 登录/锁屏首屏不加载管理员页面与全部图表实现；构建报告说明首屏字节数和分包；初始 gzip JS 相对 317.98 kB 基线明显下降，具体预算由基准设备确认 |
| D2 | 按领域拆分 `SettingsApp.vue`，继而处理 Activity、Commerce；提取表单、加载与提交逻辑 | 单个领域可独立加载、保存和验证；不以机械拆文件行数为目标；原有用户路径回归通过 |
| D3 | 引入共享请求缓存与取消策略；关闭、最小化、锁屏及后台标签页按需暂停轮询 | 同一资源不重复轮询；旧响应不覆盖新筛选/新用户；恢复时刷新；窗口销毁释放监听、计时器和请求 |
| D4 | 为桌面增加轻量导航状态：当前 App、对象、筛选、分页可恢复；跨 App 使用明确对象引用 | 刷新或分享获准链接能回到任务；没有权限时回到可访问入口；机密不进入 URL |
| D5 | 桌面保留多窗口；窄屏切换单视图任务导航，先完成密钥、用量、订阅和充值 | 在 390×844、768×1024、1440×900 下关键操作可见可达；缩放后窗口不溢出；长表格有明确的局部滚动 |
| D6 | 统一弹窗、通知、表格状态、数字格式、键盘焦点和减少动画设置 | 键盘可完成核心任务，弹窗可聚焦/关闭/返回触发点，危险操作不抢焦点；验证浅色、深色、长文本、空/错/加载状态 |

桌面命名优先表达业务对象，例如“API 密钥”“使用记录”“订单管理”。“访达”“终端”等可作为工具名称，但不以复刻操作系统能力作为功能承诺。启动动画与装饰工具应能跳过，不增加业务等待。

## 阶段 E：验证组件复用，再决定框架化

只有在一个控制台业务闭环稳定、且第二个真实消费者出现后推进。

1. 将 `mac-ui-core` 中产品名称、账号余额、固定 App ID、业务菜单和资源路径改为注入参数或插槽。
2. 产品层负责会话、授权、业务能力和启动策略；组件层负责窗口几何、焦点、键盘、主题和交互。
3. 将 `AppDefinition.component: any` 等边界收紧；明确公共 API、主题资源、浏览器兼容和打包导出。
4. 使用不含 Sub2API 的第二个小型业务系统验证：无需复制业务 store、修改核心源码或补齐隐式全局 CSS 即可运行。
5. 达标后再讨论独立发布、版本策略、文档站和插件系统。

当前不优先投入：继续增加装饰 App、追求未经测量的帧率指标、迁移到另一套前端框架、重写 Go 业务内核、先建设通用插件市场。

## 验证分层与发布闸门

| 层次 | 验证内容 | 不能据此推出 |
| --- | --- | --- |
| 本地静态与构建 | 类型、构建、发布文件清单、端点约束 | API 兼容、交易正确 |
| 隔离交互与契约测试 | 登录/角色切换、弹窗竞争、错误恢复、接口响应结构、手机布局 | 真实后端或支付平台已验收 |
| 专用集成环境 | 固定后端版本、真实角色、测试对象、请求/用量/费用关联、支付沙箱 | 所有版本和生产数据均兼容 |
| 上线前演练 | 干净部署、升级、数据保留、备份恢复、回滚与观察 | 后续可省略版本兼容检查 |

发布必须满足：阻断项关闭、支持矩阵明确、核心路径通过、无默认可用凭据、发布包不含工作区数据、回滚可执行。涉及真实扣费、生产升级、配置切换或凭据轮换时按当次明确授权执行。

## 依赖与估算

建议顺序：`A → B → D`，`C` 的基线建设与 B 并行，完整交付演练在 B 之后；`E` 由第二个消费者触发。

初步工作量仅作排期起点：A 约 4–8 人日；B 约 10–18 人日；C 约 4–8 人日；D 按场景约 6–12 人日。假设由熟悉 Vue 的开发者实施，并有后端人员提供固定版本和测试环境；不包含补齐上游本身缺失的能力、外部平台审批或生产迁移。A/C 完成后根据契约测试结果重新估算。

首轮应形成一个可审查的变更集：**网关边界修复、会话与启动守卫、危险操作防重入、对应的隔离验证记录**。不要将大规模页面重排混入这批修复。
